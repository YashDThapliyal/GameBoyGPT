# Technical report

## The question

A Game Boy has an 8-bit CPU at 4.194304 MHz, no multiply instruction and 8 KiB of RAM. Can it run a real attention-based language model as part of an actual game, and which software changes make that faster?

Results below are from an emulated DMG, using PyBoy's cycle counter cross-checked against SameBoy. No physical unit was tested. All numbers are in [RESULTS.md](RESULTS.md), which is generated from raw measurements.

## Designing a language the model can learn

A 15K-parameter model can't write free prose, so the task was shaped to fit. The world's engine decides what happens, then the model gets five symbolic tokens (`<BOS> ROOM INV ACT OUT`) and narrates in a 67-word vocabulary. That split has two benefits: narration can't break the rules, and the model gets exactly the information it needs.

The grammar composes action clauses, room nouns, adjectives and inventory phrases, so generalizing means combining parts in new ways. Held-out data are whole situations never seen in training. Greedy and sampled decoding on the integer reference were 100% grammar-valid across all 283 reachable situations, including all held-out ones. A harder test trained a fresh model on only 60% of situations, and it scored 98.8% on the 85 it never saw. Those numbers describe a narrow task: untrained weights scored 0% strict validity, and the grammar is deliberately small.

Near-top sampling gives variety and is deterministic, so it's verified bit for bit as well.

## Making the math fit

Everything is int8 in [-127, 127]. Removing -128 means `|x|` always fits in 7 bits and one multiply serves every operation. Three substitutions make the transformer integer-friendly, and QAT trains the weights under each one, so nothing is converted after the fact:

- **Normalization:** mean-absolute value and a gain table replace LayerNorm's square root and division.
- **Softmax:** max-subtract, an exponential table and a reciprocal table replace it, with the weights renormalized to sum to about 128.
- **Activation:** ReLU.

Fake quantization barely moved test NLL (0.3101 vs 0.3100 nats/token), so QAT cost nothing measurable here.

## Verification first

`reference/fixed_point.py` came before any assembly. It uses Python integers only, shares no code with the trainer, and defines every rounding and saturation rule. The kernels were then tested one at a time through a command loop in a test ROM: the harness writes inputs to WRAM, runs a command and compares memory to the reference. This caught problems immediately, including a clobbered register in the sampler.

Then the audits:

- Masked logits and token traces match the reference across 20 scenarios, greedy and sampled.
- Full journeys to the ending match, including the on-screen text.
- Patching output weights inside the ROM changes narration to exactly what the reference predicts.
- A host-free self-test ROM reports the same verdict and frame counts on two emulators.

## The baseline

V0 is plain: shift-and-add multiply, a call per MAC, K and V recomputed every token. It's what a careful first port looks like, and it's not deliberately slow. It takes 5.8 s/token, or about a minute per event, and two-thirds of that goes on recomputing K and V.

## What made it faster

From 5.805 to 0.634 s/token, 9.16x, with identical tokens. Each experiment, including what didn't work, is in [docs/PERFORMANCE.md](docs/PERFORMANCE.md).

The results didn't follow the spec's expectations. Bank layout, the headline idea going in, saved 0.13%. Streaming attention was meant to reduce RAM and instead added 32 bytes. The largest gains came from not doing work: not recomputing K and V, not computing rows the decoder can't choose, not multiplying by zero. The next came from plain kernel engineering: inline the MAC, keep operands where they're cheap to read. A 4 KiB nibble table lost to a 1 KiB quarter-square table on both speed and size.

## The game

Words reach the screen as they're generated. The main thread does inference while the VBlank ISR uploads dirty rows of a WRAM shadow map, so there's never a frozen screen, and the progress bar and token counter reflect real progress. The stats page shows seconds per token as timed on the device from LCD frames, and those frames agree with the emulator's cycle count to within 0.1%.

World layouts are seeded and verified solvable. Art and font are original and generated by a script.

## What went wrong along the way

Tests found each of these, and all are now covered by tests or documented:

1. **A softlock.** A dead-end room before the cave left players stuck without the lamp. The reachability search found it on seed 0.
2. **Dropped VRAM writes.** Uploading 6 rows per VBlank overran mode 1, which dropped the first characters of a row. The limit is now 4.
3. **A dirty-row race.** A direct shadow write after a row's dirty mark could be missed if a VBlank landed between them. The symptom appeared only on the fastest build, because timing changed, even though the bug was in every variant.
4. **A units bug in the sampling margin.** It made sampled text nonsense while greedy text looked perfect. The evaluator caught it.
5. **Non-reproducible training.** Multithreaded training on the same seed gave different weights. Training is now single-threaded and byte-reproducible, and everything was re-measured on the final weights.
6. **A misleading metric.** An early report called a 20.5% action score "close to chance." Untrained weights scored the same 20.5%, which exposed the real cause: WIN and LOSE sentences name no action, so they pass that check by default. The metric now excludes them.
7. **A hardware hazard, found by reading the code.** The LCD could be disabled right after a VBlank wait without re-checking LY. Doing that outside VBlank can damage a real screen. It now re-checks.

## Limitations and future work

- Run it on a physical DMG with a flash cartridge. The SP-stream kernel is the part most in need of that.
- Measure power, which an emulator can't do.
- Try a larger model, more rooms and longer sentences. There's plenty of ROM and RAM left, and time is the constraint.
- Try compiled weights and a grammar mask, as described in the performance doc.
- Run a human rating study. None was done.
