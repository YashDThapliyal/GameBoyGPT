How it beat a plain forward pass

Each step keeps the ones above it and has to write exactly the same tokens. Bars show the recorded time left for one reply, with inference alone.

  1. Plain forward pass

    The baseline. Every multiply is shift-and-add, and every token recomputes attention for all the tokens before it.

    Where we started.

  2. Bank layout

    Keeps tensors in one ROM bank and skips repeat bank switches. Barely helped, because no tensor here crosses a bank in a hot loop.

    Framing from FlashAttention: treat data movement as a cost.

  3. Quarter-square multiply

    Replaces shift-and-add with two table lookups, which is the identity at the bottom of the About page.

    A classic maths trick. We also tried a nibble table, and it lost.

  4. Fused dot product, row pruning

    Runs each row as one unrolled loop instead of calling multiply each time, and skips words that can't be chosen. The first token only scores 8 faces.

    From our own profiling.

  5. Sparse attention

    Skips attention weights that rounded to zero. Attention is a small share of the time, so the gain is small.

    Same idea as the zero skips in chatgbc.

  6. Cached attention

    An earlier token's keys and values never change in a one-layer model, so each is computed once. This is why token time stops growing with context.

    Standard transformer practice. gbc-transformer also caches them.

  7. Weights through the stack pointer

    Reads weights with pop, the fastest way to read in sequence on this CPU. Interrupts are held off per row, and it's untested on hardware.

    Technique also used in the Elyan Labs fork, which warns about the same risk.

  8. Zero-column skip

    An activation of zero makes a whole column of products zero, so that column is skipped.

    Same idea as the zero skips in chatgbc.

  9. Per-token head tables

    Scoring 763 tokens from 16 inputs is the slowest part. So it builds a times table for each input, then every multiply is one lookup. Uses 8 KB of cartridge RAM.

    Found in our own profile. Closest earlier idea: chatgbc's 27-sum lookup.

No code was copied from any project named here. Two of them also shaped how we test: chatgbc for checking a ROM against an integer reference, and Elyan Labs for measuring every change as its own step. The 16-unit bottleneck isn't listed because it changes the model, so it had to pass a quality check instead.
